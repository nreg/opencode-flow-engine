# 模型路由体系

> 本文档总结 opencode-flow-engine 的**模型路由逻辑**——模型如何被选择、按什么优先级解析、如何降级兜底、如何通过 `model_type` 做 per-call 动态路由。
> 相关文档：`docs/智能体配置模型体系-v1.1.0.md`（配置结构视角）、`docs/research/opensquilla-调研.md`（SquillaRouter 借鉴调研）。
> 对应版本：v1.1.1（内置默认模型链移除 + 用户配置单一来源）。
>
> **v1.1.1 变更**：运行时已删除 `DEFAULT_MODELS` / `DEFAULT_FALLBACKS` / `DEFAULT_PROFILE_MODELS` 全部内置兜底符号。模型解析**只读用户配置**（`modelProfiles` 与 per-agent 配置），未配置时返回 `provenance: 'unconfigured'`，由 OpenCode 使用其默认模型，不再注入任何内置默认模型。

## 一、路由总览

模型路由回答一个问题：**调用一个子代理时，用哪个模型？**

```text
调用方（sFlow / 横向命令）
    │  call_flow_agent(prompt, subagent_type, model_type?)
    ▼
┌─────────────────────────────────────────────────────────┐
│ call-flow-agent.ts（工具层）                              │
│   model_type 校验 → 决定档位信号 → 调用 resolveModelWithFallback │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│ agent-builder.ts（解析引擎）                              │
│   7 级优先级链 + 2 源 fallback 链 + 黑名单 + provenance     │
└──────────────────────────┬──────────────────────────────┘
                           ▼
                    resolved model
                           │  provider/glm-5.1
                           ▼
┌─────────────────────────────────────────────────────────┐
│ session.prompt({ body: { agent, parts,                   │
│     model: { providerID, modelID } } })                  │
│   ← @opencode-ai/sdk v1 官方字段（类型安全）               │
└─────────────────────────────────────────────────────────┘
```

**核心代码位置：**
- 解析引擎：`packages/plugin-infra/src/agents/agent-builder.ts`（`resolveModelWithFallback`，L365）
- 工具层：`packages/plugin-infra/src/tools/call-flow-agent.ts`（model_type 校验与注入）
- 档位定义：`agent-builder.ts` L13（`ModelTier`）、L18（`VALID_MODEL_TIERS`）

## 二、六档档位体系

`ModelTier = 'lite' | 'quick' | 'standard' | 'deep' | 'ultra' | 'review'`（`agent-builder.ts:13`）

| 档位 | 语义 | 推荐特征 | 静态 Agent 绑定 |
|------|------|---------|----------------|
| `lite` | 单行修复/零散小改 | 免费模型、小上下文 | **无**（动态路由目标） |
| `quick` | 机械性执行任务 | 高并发、指令遵循高、上下文 200-256K | `release-archivist`, `iflow-shipper` |
| `standard` | 通用编排/探索 | 中并发、代码能力强、上下文 200-256K | `need-explorer`, `ui-director`, `spec-merger`, `flow-intel`, `flow-evolve`, `iflow-discuss-planner`, `iflow-researcher` |
| `deep` | 最强代码能力 | 中并发、代码最强、上下文 200-256K | `spec-writer`, `contract-builder`, `build-executor`, `bug-investigator`, `ui-implementer`, `flow-architect`, `flow-restyle`, `iflow-plan-executor` |
| `ultra` | 复杂波次/长上下文 | 中并发、上下文 512K-1M | **无**（动态路由目标 + 波次密集任务显式路由） |
| `review` | 审查专用（角色档） | 审查能力优先 | `code-reviewer`, `test-engineer`, `review-engineer`, `flow-health`, `iflow-verifier` |

**关键规则：**
- `lite` / `ultra` **无静态绑定**，只能通过 `model_type` 参数显式路由
- 主智能体 `sFlow` / `iFlow` **不在** `AGENT_PROFILES` 中（绕过档位解析，见 §五）
- 档位集合为**闭集**（`VALID_MODEL_TIERS` 硬编码），无动态扩展机制；无效 `model_type` 会被工具层拒绝

## 三、模型解析优先级链

`resolveModelWithFallback(name, model, configOverrides, overrides, profileOptions, modelType)`（`agent-builder.ts:365`）

**双目录并存优先级**：`detectActiveWorkflow` 优先检测 `.flow-engine/iflow`（存在即返回 `'iflow'`），其次 `.flow-engine/sflow`，均不存在返回 `'none'`。此优先级决定 `activeWorkflow` 值，影响 Priority 5 静态档位绑定的生效条件。

**7 级优先级（从高到低）：**

| 优先级 | 来源 | 行为 | Provenance |
|--------|------|------|-----------|
| 1 | `overrides[name].model`（程序化 override） | 直接返回 | `override` |
| 2 | `model` 参数（调用时传入） | 直接返回 | `override` |
| 3 | **`modelType` 显式传入** | 最高档位信号，按该档位解析（用户 tier 模型 + 完整 fallback） | `profile` / `provider-fallback` |
| 4 | `configOverrides[name].model`（per-agent 配置） | **跳过档位解析直接使用**；不可用时先试 per-agent fallbacks | `config-override` |
| 5 | `AGENT_PROFILES[name]` → 用户 `modelProfiles.<tier>.model` | 静态档位绑定解析（`activeWorkflow === 'sflow' \|\| activeWorkflow === 'iflow'`） | `profile` |
| 6 | fallback 链 | per-agent 用户配置 → 用户档位配置，首个可用模型 | `provider-fallback` |
| 7 | 链尾 | 无用户配置 → `model: undefined`（不注入模型，交由 OpenCode 默认模型） | `unconfigured` |

**实现要点（`agent-builder.ts:360-476`）：**
- 解析**只读用户配置**，运行时不存在任何内置默认模型或内置 fallback 列表
- Priority 3（modelType）：`tierConfig = profileOptions?.modelProfiles?.[tier]`——仅读用户配置；未配置则落入后续优先级，不再回退内置默认；主模型不可用时走完整 fallback 链
- Priority 4（configModel）：模型可用即返回（跳过档位）；不可用则先试 `configOverrides[name].fallback_models`，再落入后续 tier 解析（`agent-builder.ts:417-432`）
- Priority 5（静态绑定）：当 `activeWorkflow === 'sflow'` 或 `'iflow'` 且该 agent 在 `AGENT_PROFILES` 中才生效

**实现细节**：`call_flow_agent` 的 `model_type` 路由在调用 `resolveModelWithFallback` 时使用常量 `activeWorkflow: 'sflow'`（不做动态目录检测）。因为 Priority 3（modelType）先于 Priority 5 返回，且门控条件对 `'sflow'` 与 `'iflow'` 放行语义等价，动态检测只会增加无意义的文件系统 I/O。

## 四、Fallback 链

**顺序（R9 规范，`buildFallbackChain`，`agent-builder.ts:318-323`）：**

```text
agents[name].fallback_models（per-agent 用户配置）
  → modelProfiles.<tier>.fallback_models（用户档位配置）
```

> 链尾不再追加任何内置默认（`DEFAULT_PROFILE_MODELS.<tier>.fallback_models` 与 `DEFAULT_FALLBACKS[name]` 已于 v1.1.1 从运行时移除）。

**行为规则：**
- **按优先级取第一个非空链**：空数组（`[]`）视为"跳过此级"，继续下一非空源
- `tryFallbackChain`（`agent-builder.ts:328-340`）：记录 `attempted` 数组（含主模型），返回第一个 `isModelAvailable` 通过的模型
- 全部不可用 → 落到链尾 `{ model: undefined, provenance: 'unconfigured' }`，调用方不注入 model 字段，由 OpenCode 使用其默认模型
- 黑名单（`UNAVAILABLE_MODELS`，见 §六）参与 `isModelAvailable` 判断

**典型场景（带优先级链 + fallback 链的完整组合）：**

| 场景 | 解析路径 |
|------|---------|
| 常规调用，无任何覆盖 | Priority 5 → 静态档位 → 用户档位模型 |
| `model_type='ultra'` 显式路由 | Priority 3 → ultra 档模型 → 不可用则 per-agent → user tier |
| per-agent 配了 model | Priority 4 → 直接使用（跳过档位）→ 不可用则 per-agent fallbacks → 继续档位解析 |
| 档位模型挂了 | Priority 5 命中但不可用 → Priority 6 fallback 链 → 全失败 → Priority 7 `unconfigured` |
| 用户未配置任何模型 | Priority 7 → `unconfigured`，使用 OpenCode 默认模型 |

## 五、主智能体绕过规则

`sFlow` / `iFlow` 主智能体**不参与档位路由**：

- 不在 `AGENT_PROFILES` 中（`agent-builder.ts` 无其条目）
- 模型解析直接走 Priority 1/2/4/7：`overrides` → `model` 参数 → `agents` 配置 → 链尾 `unconfigured`
- 用户为其配置 `model` + `fallbackModels` 于 `agents` 段即可（`config.example.json` 示例）
- 未配置时不注入 model，主智能体使用 OpenCode 默认模型

**目的：** 编排者的模型选择应与子代理的解耦——主智能体承载对话策略，档位体系服务于任务分发。

## 六、运行时故障转移（黑名单 + 自动换模型）

```typescript
markModelUnavailable(model: string, opts?: { resetAt?: number | null; ttlMs?: number })   // 将故障模型加入黑名单（TTL 语义，单调取更长 expireAt）
clearUnavailableModels()              // 清空（测试/刷新）
isModelAvailable(model)               // 解析时跳过黑名单模型（TTL 过期惰性删除）
```

### 触发机制

运行时模型调用失败后，`call-flow-agent.ts` **自动**调用 `markModelUnavailable()` 将故障模型加入 `UNAVAILABLE_MODELS` 集合，并在同一 session 上换模型重新 prompt。触发点：

1. **sync 模式**：`runWithModelFallback` 编排器在以下情况触发——
   - `pollSessionCompletion` 返回 `null`（OpenCode 重试耗尽）；
   - poll 返回的错误码报错（`classifyModelErrorByCode`，仅错误码驱动）或用户 prompt 回显（错误码报错不算成功）；
   - send 阶段 HTTP status 分类为瞬态/非瞬态失败。
2. **async 模式**：`createBackgroundTaskWatcher`（probe 模式）与 `pollAndComplete` 在检测到 `null` **或错误码报错**时调用 `tryAsyncModelFallback` 触发——错误码报错不判 `completed`；polling 层 probe 对配额/错误引起的 retry 态回传错误文本（不再无限 `PROBE_PENDING`）。watcher 故障转移同时补传用户配置 fallback 链（`extraFallbacks`）。

> **分类判据 = 仅错误码**：`classifyModelErrorByCode` 只认机器可读的错误码（send 阶段 HTTP status、错误文本嵌入的 JSON `"code"`/`"status"` 字段、行首前缀码如 `401：`/`402: `）。基于错误文案措辞的文本模式分类兜底（`classifyQuotaError` / `matchesModelErrorPatterns` / `QUOTA_ERROR_PATTERNS`）已删除。**无错误码的报错无法分类是可接受的已知限制**。`parseQuotaResetTime` 保留，仅用于错误码判定 non-transient 后从同一文本提取重置时长作为冷却时长（解析不出给默认 TTL）。

### 黑名单 TTL 语义（长冷却）

- **transient 错误**（poll null / 错误码瞬态报错 / send 非 429）：默认 5 分钟冷却
- **非瞬态错误**（401/402/403/404 或配额类错误码，带重置时间）：长冷却**至重置时间**（下限 30 分钟，上限 7 天；解析不出重置时间给默认 TTL 30 分钟）
- **单调合并**：同一模型多次 `markModelUnavailable` 时取更长 `expireAt`（max）——后续的默认 5min 标记**不会覆盖**已写入的长冷却 TTL

### 换模型链路

- **必须**使用 `getAlternativeModel(currentModel, agentName, extraFallbacks)`（`agent-builder.ts`），**不得**使用 `resolveModelWithFallback`（其 P1/P2/P6 分支不做同义换模）
- `getAlternativeModel` 遍历**用户配置链** `extraFallbacks`（per-agent `fallbackModels` + 用户档位，由 `buildAgentFallbackChain` 构建），返回第一个不同于 `currentModel` 且 `isModelAvailable` 通过的模型；找不到返回 `null`
- 链中**不含任何内置默认模型**（`DEFAULT_FALLBACKS` 已于 v1.1.1 移除）——未配置 fallback 时换模型不会发生，重试终止于条件 ①

### 终止条件（三重保障）

| 条件 | 判定 | 语义 |
|------|------|------|
| ① 无替代模型 | `getAlternativeModel` 返回 `null` | fallback 链耗尽 |
| ② 重复模型 | `attemptedModels.includes(next)` | 防止 fallback 链退化无限循环 |
| ③ 次数上限 | `attemptedModels.length > MAX_MODEL_RETRIES` | `MAX_MODEL_RETRIES = 2`，即首模型 + 最多 2 次换模型 = 最多 3 次 prompt |

### 豁免规则

- **ContextOverflowError**：既不拉黑也不换模型，交给 runtime auto-compaction 处理
- **HTTP 400/404**：前置校验失败（SessionBusy / model not found / agent 不存在），不拉黑不换模型，直接返回错误

### 可观测性

- 成功后 `backgroundTaskRegistry.resolvedModel` 为最终生效模型（非初始模型）
- 换模型过程写入 `model_fallback` 事件（`store.appendEvent`）
- 返回体携带 `attempted_models` / `model_fallbacks` 字段
- 重试原样重发 basePrompt（`buildAttemptPrompt` 直通，接管轮次声明已移除，上下文由 session 承载）

### 配置缓存

- 配置缓存 30 秒 TTL（`clearConfigCache()` 手动失效）

## 七、Per-Call 动态路由（model_type）

**工具签名：** `call_flow_agent(prompt, subagent_type, model_type?)`

**路由决策（sFlow 侧，`<Model_Tier_Rules>` 指南）：**

| 场景 | model_type |
|------|-----------|
| 单行/零散小改 | `lite` |
| 机械性执行（归档/格式化）或 explore 探索 | `quick` |
| 常规子任务 | `standard` |
| 代码执行 | `deep` |
| 波次任务依赖紧密且任务数量多、需长上下文 | `ultra` |
| 审查类 | `review` |

**工具层流程（`call-flow-agent.ts`）：**
1. `model_type` 可选参数，取值校验于 `VALID_MODEL_TIERS`（无效 → `formatToolError` 列出有效档位）
2. 已传 → 作为 `modelType` 传给 `resolveModelWithFallback`（Priority 3，最高档位信号）
3. 未传 → 走静态绑定（Priority 4/5 正常链）
4. 解析出的 `provider/model` 字符串 → `parseModelString` 拆分为 `{ providerID, modelID }`
5. 注入 `session.prompt` body.model（sync / async 模式均支持）

**设计决策：** **无 prompt 启发式评估器**——档位选择完全由 sFlow 主智能体按指南自行判断（LLM 决策），工具层只做校验与解析，不猜测任务复杂度。

## 八、Provenance 追踪

每次解析返回 `ModelResolutionResult`：

```typescript
interface ModelResolutionResult {
  model: string | undefined;   // undefined = 未配置（provenance 'unconfigured'）
  provenance: 'override' | 'config-override' | 'profile' | 'provider-fallback' | 'unconfigured';
  fallbackAttempted?: string[];  // 尝试过的模型列表（含主模型）
}
```

> v1.1.1：`system-default` provenance 已随内置默认模型移除，新增 `unconfigured` 表示"用户未配置模型，不注入 model 字段"。

**用途：** 排障"为什么这个子代理用了这个模型"——provenance 指明来源层级，`fallbackAttempted` 指明经历了哪些降级。与 opensquilla 的 decision log 理念一致（调研报告 P0-4）。

## 九、设计溯源

本体系的部分设计参考了 OpenSquilla SquillaRouter（详见 `docs/research/opensquilla-调研.md`）：

| OpenSquilla 概念 | 本项目对应 |
|-----------------|-----------|
| C0-C3 四层 tier | lite/quick/standard/deep/ultra 六档（更细粒度） |
| 3 层降级链（ML→启发式→默认） | fallback 链（per-agent → user tier），无内置兜底 |
| provider mismatch veto | 档位解析在 sflow 和 iflow 工作流生效（none 跳过） |
| rollout observe/prompt_only/full | 未采用（现阶段不需要灰度） |
| ML 特征路由（390 维） | **未采用**——改为 sFlow LLM 显式决策 + 静态绑定（避免引入 Python/ML 依赖） |

**关键差异：** OpenSquilla 用 ML 模型每轮自动分类路由；本项目由 sFlow 主智能体（LLM）结合工作流上下文显式决策 `model_type`，工具层兜底静态绑定。前者成本优化更激进，后者更可控、零额外依赖。

## 十、常见问题排查

| 现象 | 排查方向 |
|------|---------|
| 子代理用了非预期模型 | 检查 `fallbackAttempted` + `provenance`：是走了 fallback 还是档位绑定？ |
| 单行修改却用了大模型 | sFlow 未传 `model_type` → 走了静态绑定（如 build-executor → deep）。需 sFlow 按 `<Model_Tier_Rules>` 显式传 `lite` |
| `lite`/`ultra` 从未被用 | 它们是动态目标，必须显式 `model_type` 才生效；确认 sFlow 提示词决策指南生效 |
| 模型报错后一直失败 | 是否被 `markModelUnavailable` 拉黑？`clearUnavailableModels()` 重置 |
| 模型故障后自动换了模型 | 正常行为：运行时故障转移已启用。检查返回体 `model_fallbacks` 字段确认转移链路 |
| 故障转移未触发 | 检查是否为 ContextOverflow（不触发转移）或 HTTP 400/404 前置校验失败（不触发转移） |
| 换模型后仍失败 | `MAX_MODEL_RETRIES=2` 限制最多 3 次 prompt；用户配置的 fallback 链可能已全部拉黑 |
| 档位配置不生效 | 检查 `modelProfiles` 是否为新 6 档对象格式（旧 string 格式会警告并忽略）；`activeWorkflow` 是否 sflow 或 iflow |
| 子代理用了 OpenCode 默认模型 | 正常行为：`provenance='unconfigured'` 表示该档位/该 agent 未配置任何用户模型。在 `modelProfiles.<tier>` 或 `agents.<name>` 中配置 `model` 即可 |
