# 模型路由体系

> 本文档总结 opencode-flow-engine 的**模型路由逻辑**——模型如何被选择、按什么优先级解析、如何降级兜底、如何通过 `model_type` 做 per-call 动态路由。
> 相关文档：`docs/智能体配置模型体系-v1.1.0.md`（配置结构视角）、`docs/research/opensquilla-调研.md`（SquillaRouter 借鉴调研）。
> 对应版本：v1.1.0（模型档位体系重构 + per-call 动态路由 L1-B）。

---

## 一、路由总览

模型路由回答一个问题：**调用一个子代理时，用哪个模型？**

```text
调用方（sFlow / 横向命令）
    │  call_flow_agent(prompt, subagent_type, model_type?)
    ▼
┌─────────────────────────────────────────────────────────┐
│ call-flow-agent.ts（工具层）                              │
│   model_type 校验 → 决定档位信号 → 调用 resolveModelWithFallback │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│ agent-builder.ts（解析引擎）                              │
│   8 级优先级链 + 4 级 fallback 链 + 黑名单 + provenance     │
└──────────────────────────┬──────────────────────────────┘
                           ▼
                    resolved model
                           │  provider/glm-5.1
                           ▼
┌─────────────────────────────────────────────────────────┐
│ session.prompt({ body: { agent, parts,                   │
│     model: { providerID, modelID } } })                  │
│   ← @opencode-ai/sdk v1 官方字段（类型安全）               │
└─────────────────────────────────────────────────────────┘
```

**核心代码位置：**
- 解析引擎：`packages/plugin-infra/src/agents/agent-builder.ts`（`resolveModelWithFallback`，L365）
- 工具层：`packages/plugin-infra/src/tools/call-flow-agent.ts`（model_type 校验与注入）
- 档位定义：`agent-builder.ts` L13（`ModelTier`）、L18（`VALID_MODEL_TIERS`）

## 二、六档档位体系

`ModelTier = 'free' | 'quick' | 'standard' | 'deep' | 'ultra' | 'review'`（`agent-builder.ts:13`）

| 档位 | 语义 | 推荐特征 | 静态 Agent 绑定 |
|------|------|---------|----------------|
| `free` | 单行修复/零散小改 | 免费模型、小上下文 | **无**（动态路由目标） |
| `quick` | 机械性执行任务 | 高并发、指令遵循高、上下文 200-256K | `release-archivist` |
| `standard` | 通用编排/探索 | 中并发、代码能力强、上下文 200-256K | `need-explorer`, `ui-director`, `spec-merger`, `flow-intel`, `flow-evolve` |
| `deep` | 最强代码能力 | 中并发、代码最强、上下文 200-256K | `spec-writer`, `contract-builder`, `build-executor`, `bug-investigator`, `ui-implementer`, `flow-architect`, `flow-restyle` |
| `ultra` | 复杂波次/长上下文 | 中并发、上下文 512K-1M | **无**（动态路由目标 + 波次密集任务显式路由） |
| `review` | 审查专用（角色档） | 审查能力优先 | `code-reviewer`, `test-engineer`, `review-engineer`, `flow-health` |

**关键规则：**
- `free` / `ultra` **无静态绑定**，只能通过 `model_type` 参数显式路由
- 主智能体 `sFlow` / `iFlow` **不在** `AGENT_PROFILES` 中（绕过档位解析，见 §五）
- 档位集合为**闭集**（`VALID_MODEL_TIERS` 硬编码），无动态扩展机制；无效 `model_type` 会被工具层拒绝

## 三、模型解析优先级链

`resolveModelWithFallback(name, model, configOverrides, overrides, profileOptions, modelType)`（`agent-builder.ts:365`）

**8 级优先级（从高到低）：**

| 优先级 | 来源 | 行为 | Provenance |
|--------|------|------|-----------|
| 1 | `overrides[name].model`（程序化 override） | 直接返回 | `override` |
| 2 | `model` 参数（调用时传入） | 直接返回 | `override` |
| 3 | **`modelType` 显式传入** | 最高档位信号，按该档位解析（tier 模型 + 完整 fallback） | `profile` / `provider-fallback` |
| 4 | `configOverrides[name].model`（per-agent 配置） | **跳过档位解析直接使用**；不可用时先试 per-agent fallbacks | `config-override` |
| 5 | `AGENT_PROFILES[name]` → 用户 `modelProfiles.<tier>.model` | 静态档位绑定解析（仅 `activeWorkflow === 'sflow'`） | `profile` |
| 6 | `DEFAULT_PROFILE_MODELS.<tier>.model` | 内置档位默认（用户未配置时兜底） | `profile` |
| 7 | fallback 链 | 4 级拼接，首个可用模型 | `provider-fallback` |
| 8 | `DEFAULT_MODELS[name]` | 系统最终默认 | `system-default` |

**实现要点（`agent-builder.ts:373-414`）：**
- Priority 3（modelType）：`tierConfig = profileOptions?.modelProfiles?.[tier] ?? DEFAULT_PROFILE_MODELS[tier]`——用户配置优先，未配置回退内置默认；主模型不可用时走完整 fallback 链
- Priority 4（configModel）：模型可用即返回（跳过档位）；不可用则先试 `configOverrides[name].fallback_models`，再落入后续 tier 解析（`agent-builder.ts:417-432`）
- Priority 5（静态绑定）：仅当 `activeWorkflow === 'sflow'` 且该 agent 在 `AGENT_PROFILES` 中才生效

## 四、Fallback 链

**顺序（R9 规范，`buildFallbackChain`，`agent-builder.ts:325-332`）：**

```text
agents[name].fallback_models（per-agent 用户配置）
  → modelProfiles.<tier>.fallback_models（用户档位配置）
  → DEFAULT_PROFILE_MODELS.<tier>.fallback_models（内置档位默认）
  → DEFAULT_FALLBACKS[name]（legacy agent 级内置）
```

**行为规则：**
- **按优先级取第一个非空链**：空数组（`[]`）视为"跳过此级"，继续下一非空源
- `tryFallbackChain`（`agent-builder.ts:337-349`）：记录 `attempted` 数组（含主模型），返回第一个 `isModelAvailable` 通过的模型
- 全部不可用 → 回退 `DEFAULT_MODELS[name]`（`system-default`）
- 黑名单（`UNAVAILABLE_MODELS`，见 §六）参与 `isModelAvailable` 判断

**典型场景（带优先级链 + fallback 链的完整组合）：**

| 场景 | 解析路径 |
|------|---------|
| 常规调用，无任何覆盖 | Priority 5 → 静态档位 → 用户/内置档位模型 |
| `model_type='ultra'` 显式路由 | Priority 3 → ultra 档模型 → 不可用则 per-agent → user tier → default tier → DEFAULT_FALLBACKS |
| per-agent 配了 model | Priority 4 → 直接使用（跳过档位）→ 不可用则 per-agent fallbacks → 继续档位解析 |
| 档位模型挂了 | Priority 5 命中但不可用 → Priority 7 fallback 链 → 全失败 → Priority 8 系统默认 |

## 五、主智能体绕过规则

`sFlow` / `iFlow` 主智能体**不参与档位路由**：

- 不在 `AGENT_PROFILES` 中（`agent-builder.ts` 无其条目）
- 模型解析直接走 Priority 1/2/4/8：`overrides` → `model` 参数 → `agents` 配置 → `DEFAULT_MODELS`
- 用户为其配置 `model` + `fallbackModels` 于 `agents` 段即可（`config.example.json` 示例）

**目的：** 编排者的模型选择应与子代理的解耦——主智能体承载对话策略，档位体系服务于任务分发。

## 六、运行时故障转移（黑名单）

```typescript
markModelUnavailable(model: string)   // 将故障模型加入黑名单
clearUnavailableModels()              // 清空（测试/刷新）
isModelAvailable(model)               // 解析时跳过黑名单模型
```

- 运行时某个模型调用失败后，可调用 `markModelUnavailable()` 将其加入 `UNAVAILABLE_MODELS` 集合
- 之后所有解析（含 fallback 链）自动跳过该模型
- 配置缓存 30 秒 TTL（`clearConfigCache()` 手动失效）

## 七、Per-Call 动态路由（model_type）

**工具签名：** `call_flow_agent(prompt, subagent_type, model_type?)`

**路由决策（sFlow 侧，`<Model_Tier_Rules>` 指南）：**

| 场景 | model_type |
|------|-----------|
| 单行/零散小改 | `free` |
| 机械性执行（归档/格式化）或 explore 探索 | `quick` |
| 常规子任务 | `standard` |
| 代码执行 | `deep` |
| 波次任务依赖紧密且任务数量多、需长上下文 | `ultra` |
| 审查类 | `review` |

**工具层流程（`call-flow-agent.ts`）：**
1. `model_type` 可选参数，取值校验于 `VALID_MODEL_TIERS`（无效 → `formatToolError` 列出有效档位）
2. 已传 → 作为 `modelType` 传给 `resolveModelWithFallback`（Priority 3，最高档位信号）
3. 未传 → 走静态绑定（Priority 4/5 正常链）
4. 解析出的 `provider/model` 字符串 → `parseModelString` 拆分为 `{ providerID, modelID }`
5. 注入 `session.prompt` body.model（sync / async 模式均支持）

**设计决策：** **无 prompt 启发式评估器**——档位选择完全由 sFlow 主智能体按指南自行判断（LLM 决策），工具层只做校验与解析，不猜测任务复杂度。

## 八、Provenance 追踪

每次解析返回 `ModelResolutionResult`：

```typescript
interface ModelResolutionResult {
  model: string;
  provenance: 'override' | 'config-override' | 'profile' | 'provider-fallback' | 'system-default';
  fallbackAttempted?: string[];  // 尝试过的模型列表（含主模型）
}
```

**用途：** 排障"为什么这个子代理用了这个模型"——provenance 指明来源层级，`fallbackAttempted` 指明经历了哪些降级。与 opensquilla 的 decision log 理念一致（调研报告 P0-4）。

## 九、设计溯源

本体系的部分设计参考了 OpenSquilla SquillaRouter（详见 `docs/research/opensquilla-调研.md`）：

| OpenSquilla 概念 | 本项目对应 |
|-----------------|-----------|
| C0-C3 四层 tier | free/quick/standard/deep/ultra 六档（更细粒度） |
| 3 层降级链（ML→启发式→默认） | fallback 链（per-agent → tier → 内置 → 系统默认） |
| provider mismatch veto | 档位解析仅在 sflow 工作流生效（隔离 iFlow） |
| rollout observe/prompt_only/full | 未采用（现阶段不需要灰度） |
| ML 特征路由（390 维） | **未采用**——改为 sFlow LLM 显式决策 + 静态绑定（避免引入 Python/ML 依赖） |

**关键差异：** OpenSquilla 用 ML 模型每轮自动分类路由；本项目由 sFlow 主智能体（LLM）结合工作流上下文显式决策 `model_type`，工具层兜底静态绑定。前者成本优化更激进，后者更可控、零额外依赖。

## 十、常见问题排查

| 现象 | 排查方向 |
|------|---------|
| 子代理用了非预期模型 | 检查 `fallbackAttempted` + `provenance`：是走了 fallback 还是档位绑定？ |
| 单行修改却用了大模型 | sFlow 未传 `model_type` → 走了静态绑定（如 build-executor → deep）。需 sFlow 按 `<Model_Tier_Rules>` 显式传 `free` |
| `free`/`ultra` 从未被用 | 它们是动态目标，必须显式 `model_type` 才生效；确认 sFlow 提示词决策指南生效 |
| 模型报错后一直失败 | 是否被 `markModelUnavailable` 拉黑？`clearUnavailableModels()` 重置 |
| 档位配置不生效 | 检查 `modelProfiles` 是否为新 6 档对象格式（旧 string 格式会警告并回退内置默认）；`activeWorkflow` 是否 sflow |
