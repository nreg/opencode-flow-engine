## 1. 双轨机制概述

opencode-flow-engine 存在两套独立的技能加载机制，分别服务于不同的场景和技能类型。

### 1.1 轨道 1：skill-loader 注入

**加载机制**：
- 注入位置：`packages/plugin-infra/src/sflow-plugin-factory.ts` 的 config hook
- 注入逻辑：`skillLoader.getSkill(name)`，其中 `name` 是 agent 名（来自 `getAgentNames()` → `AGENT_REGISTRY` 的 key）
- 文件路径：只读取 `workflows/sflow/skills/<name>/SKILL.md`
- 匹配规则：只有与 agent 同名的技能目录才会被注入

**轨道 1 技能列表（11 个）**：

| 序号 | 技能目录 | 对应 Agent | 用途 |
|------|---------|-----------|------|
| 1 | `need-explorer` | need-explorer | 需求探索 |
| 2 | `spec-writer` | spec-writer | 规格编写 |
| 3 | `contract-builder` | contract-builder | 契约构建 |
| 4 | `build-executor` | build-executor | 构建执行 |
| 5 | `bug-investigator` | bug-investigator | Bug 调查 |
| 6 | `code-reviewer` | code-reviewer | 代码审查 |
| 7 | `release-archivist` | release-archivist | 发布归档 |
| 8 | `spec-merger` | spec-merger | 规格合并 |
| 9 | `ui-director` | ui-director | UI 指导 |
| 10 | `ui-implementer` | ui-implementer | UI 实现 |
| 11 | `workflow-start` | workflow-start | 工作流启动 |

**关键实现**：
- `skill-loader.ts` 的 `loadAllSkills()` 方法遍历 `workflows/sflow/skills/` 下所有目录，加载进内存 Map
- 技能通过 slash 命令 `/技能名` 触发（如 `/build-executor`）
- 技能内容注入到 agent 的系统提示中，作为执行指导

### 1.2 轨道 2：运行时 skill() 调用

**加载机制**：
- 调用方式：`skill(name="taste-skill")` —— OpenCode 原生 skill 工具调用
- 加载路径：按 OpenCode 技能发现路径加载（非 skill-loader）

**OpenCode 技能发现路径（6 个位置，2026-08-21 更新）**：

| 优先级 | 路径 | 说明 |
|--------|------|------|
| 1 | `.opencode/skills/<name>/` | 项目级原生 |
| 2 | `~/.config/opencode/skills/<name>/` | 全局原生 |
| 3 | `.claude/skills/<name>/` | 项目级 Claude 兼容 |
| 4 | `~/.claude/skills/<name>/` | 全局 Claude 兼容 |
| 5 | `.agents/skills/<name>/` | 项目级 agent 兼容 |
| 6 | `~/.agents/skills/<name>/` | 全局 agent 兼容（`npx skills add` 默认安装位置） |

**轨道 2 技能列表（18 个）**：

| 分类 | 技能目录 | 用途 |
|------|---------|------|
| **设计类** | `taste-skill` | 反模板化落地页设计 |
| | `impeccable` | UI/UX 设计质量提升 |
| | `polish` | 最终样式质量检查 |

| | `svg-architect` | SVG 图标设计 |
| | `ui-ux-pro-max` | UI/UX 设计智能 |
| | `frontend-design-pro` | 高级前端设计工作流 |
| **代码审查类** | `frontend-code-review` | 前端代码质量检查 |
| | `frontend-performance-optimization` | 前端性能优化 |
| **参考类** | `design-reference` | 设计参考资源 |
| **动画类** | `gsap-core` | GSAP 核心 API |
| | `gsap-timeline` | GSAP 时间线 |
| | `gsap-scrolltrigger` | GSAP 滚动触发 |
| | `gsap-plugins` | GSAP 插件 |

## 2. 目录分离

**架构设计原则**：两套技能物理隔离，避免误加载和冲突。

### 目录结构

```
opencode-flow-engine/
├── workflows/sflow/skills/     # 轨道 1 技能（11 个）
│   ├── need-explorer/
│   ├── spec-writer/
│   ├── contract-builder/
│   ├── build-executor/
│   ├── bug-investigator/
│   ├── code-reviewer/
│   ├── release-archivist/
│   ├── spec-merger/
│   ├── ui-director/
│   ├── ui-implementer/
│   └── workflow-start/
│
└── skills/                     # 轨道 2 技能分发源（18 个）
    ├── taste-skill/
    ├── impeccable/
    ├── polish/
    ├── shadcn-ui/
    ├── svg-architect/
    ├── ui-ux-pro-max/
    ├── frontend-code-review/
    ├── frontend-design-pro/
    ├── frontend-performance-optimization/
    ├── design-reference/
    ├── gsap-core/
    ├── gsap-timeline/
    ├── gsap-scrolltrigger/
    ├── gsap-plugins/
    ├── gsap-utils/
    ├── gsap-react/
    ├── gsap-frameworks/
    └── gsap-performance/
```

### 关键约束

**skill-loader 的 `resolveSkillsDir()` 候选路径**：
- ✅ `workflows/sflow/skills`（轨道 1 主路径）
- ✅ `workflows/iflow/skills`（IFlow 兼容路径）
- ✅ `workflows/sflow/skills`（deprecated mirror，向后兼容）
- ❌ **不包含** 项目根 `skills/`

**结果**：
- 轨道 2 技能在项目根 `skills/` 的副本**不被 skill-loader 加载**
- 运行时真正生效的是全局 `~/.agents/skills/` 中的安装副本
- 杜绝轨道 2 技能被误注入到轨道 1 agent

## 3. install-skills CLI

### 命令位置

`bin/flow-engine.js` 的 `install-skills` 子命令

### 参数说明

| 参数 | 说明 | 默认值 |
|------|------|--------|
| 无参数 | 安装全部轨道 2 技能 | - |
| `--filter <pattern>` | 按前缀过滤技能 | null（全部） |
| `--all` | 显式安装全部 | - |

### 源目录与目标目录

- **源目录**：项目根 `skills/`
  - 验证规则：
    1. 目录名必须为 `skills`
    2. 主路径验证：父目录含 `package.json`
    3. `devPath` 回退：宽松验证（允许开发环境）
- **目标目录**：`~/.agents/skills/`（全局 agent 兼容路径）

### 幂等性

- 目标目录已存在同名技能 → 跳过安装
- 重复执行不会覆盖已有技能

### 用法示例

```bash
# 安装全部轨道 2 技能
node bin/flow-engine.js install-skills

# 安装 GSAP 相关技能
node bin/flow-engine.js install-skills --filter gsap-

# 安装前端设计技能
node bin/flow-engine.js install-skills --filter frontend-

# 显式安装全部（与无参数等效）
node bin/flow-engine.js install-skills --all
```

### 安全检查

- 若源目录指向 `workflows/sflow/skills` → **拒绝执行**（防止误装轨道 1 技能）
- 错误提示：`Error: Source directory cannot be workflows/sflow/skills. Use project root skills/ instead.`

## 4. 轨道 1 隔离约束

### 硬性禁止修改的文件

以下文件是轨道 1 的核心实现，**禁止修改**：

| 文件 | 作用 | 修改风险 |
|------|------|---------|
| `packages/plugin-infra/src/sflow-plugin-factory.ts` | skill-loader 注入逻辑 | 破坏 agent 技能注入 |
| `packages/plugin-infra/src/skill-loader.ts` | 技能加载器 | 破坏技能发现和加载 |
| `packages/plugin-infra/src/agent-builder.ts` | Agent 构建器 | 破坏 agent 注册 |

### 新增技能约束

**轨道 2 新增技能时**：
- ❌ 不得放入 `workflows/sflow/skills/`（会被轨道 1 误注入）
- ✅ 放入项目根 `skills/`（分发源）
- ✅ 通过 `install-skills` 安装到全局

**轨道 1 新增技能时**：
- ✅ 放入 `workflows/sflow/skills/<agent-name>/`
- ✅ 必须与 agent 同名（否则不会被注入）
- ✅ 更新 `AGENT_REGISTRY` 注册

### install-skills 约束

- 源目录必须是 `skills/`
- 若指向 `workflows/sflow/skills` → 拒绝执行
- 防止误装轨道 1 技能到全局

## 5. 常见问题

### Q1: 为什么 9 大前端技能在 workflows/sflow/skills/ 有副本？

**A**: 那是历史遗留的分发源。早期设计将所有技能放在 `workflows/sflow/skills/`，后发现与 agent 同名技能冲突风险，遂迁移到项目根 `skills/`。

**现状**：
- `workflows/sflow/skills/` 现仅含轨道 1 技能（11 个）
- 项目根 `skills/` 含轨道 2 技能（18 个）
- 历史副本已清理

### Q2: skill-loader 会加载轨道 2 技能吗？

**A**: 不会。

**原因**：
- `resolveSkillsDir()` 的候选路径不包含项目根 `skills/`
- skill-loader 只扫描 `workflows/sflow/skills/`、`workflows/iflow/skills/` 及其 mirror
- 轨道 2 技能物理存在但不被 skill-loader 发现

### Q3: 如何通过 slash 命令触发技能？

**A**: 
- **轨道 1 技能**：可用 slash 命令（如 `/build-executor`），因为已加载进 skill-loader 的 Map
- **轨道 2 技能**：不可用 slash 命令，需用 `skill(name="taste-skill")` 原生调用

### Q4: 轨道 2 技能的真正生效位置在哪？

**A**: 全局 `~/.agents/skills/`。

**流程**：
1. 项目根 `skills/` 是分发源（随代码仓库分发）
2. `install-skills` 将其安装到全局 `~/.agents/skills/`
3. 运行时 OpenCode 从全局路径加载

### Q5: 如何验证技能加载状态？

**A**: 
```bash
# 验证轨道 1 技能（11 个）
ls workflows/sflow/skills

# 验证轨道 2 技能（18 个）
ls skills

# 验证全局安装
ls ~/.agents/skills
```

### Q6: 新增轨道 2 技能的完整流程？

**A**:
1. 在项目根 `skills/` 创建技能目录：`skills/<skill-name>/SKILL.md`
2. 编写 `SKILL.md`（遵循 OpenCode 技能格式）
3. 执行 `node bin/flow-engine.js install-skills --filter <skill-name>`
4. 验证全局安装：`ls ~/.agents/skills/<skill-name>`
5. 运行时调用：`skill(name="<skill-name>")`

### Q7: 为什么不让 skill-loader 加载所有技能？

**A**: 架构隔离考虑。

**原因**：
1. **避免命名冲突**：轨道 1 技能与 agent 同名，轨道 2 技能独立命名
2. **职责分离**：轨道 1 服务于工作流 agent，轨道 2 服务于通用设计/动画任务
3. **加载时机不同**：轨道 1 在 agent 创建时注入，轨道 2 在运行时按需调用
4. **维护成本**：两套机制独立演进，互不干扰
